# รายงานวิเคราะห์จุดปรับปรุงและสิ่งที่ควรเพิ่มเติม — AppStock

วันที่ตรวจ: 16 กันยายน 2569 (2026-09-16)

## ขอบเขตและข้อจำกัด

ตรวจโค้ดในเครื่องของหน้าคอม หน้ามือถือ ระบบออฟไลน์ Service Worker ฝั่ง Google Apps Script และขั้นตอนเผยแพร่ พร้อมอ่านเอกสารโครงการและบันทึกข้อตกลงเดิม รายงานนี้เป็นข้อเสนอเท่านั้น ไม่มีการแก้ไขโค้ด เปลี่ยนข้อมูลสต๊อก หรือเผยแพร่ระบบ

ข้อค้นพบมาจากการอ่านโค้ด ไม่ได้ทดสอบกับระบบจริง จึงยังไม่ยืนยันว่าเกิดเหตุแล้ว หรือโค้ดที่ใช้งานจริงตรงกับไฟล์ในเครื่องทุกส่วน อ้างอิงเป็นชื่อไฟล์และฟังก์ชันเพื่อค้นหาได้แม้เลขบรรทัดเปลี่ยน

ระดับความสำคัญ:

- **P1 — ควรจัดการก่อน:** เสี่ยงต่อยอดสต๊อก งานสูญหาย หรือการทำรายการโดยไม่มีสิทธิ์
- **P2 — ควรทำตามมา:** เพิ่มความน่าเชื่อถือ ลดงานแก้ไขและความผิดพลาดในการใช้งาน
- **P3 — ต่อยอด:** เพิ่มความสะดวกและข้อมูลเพื่อบริหารงาน

## สิ่งที่ระบบมีอยู่แล้วและควรรักษาไว้

- มีคิวออฟไลน์และรหัสรายการ `opId` สำหรับป้องกันการส่งซ้ำ ไม่จำเป็นต้องเริ่มพัฒนาออฟไลน์ใหม่ทั้งหมด
- มีการล็อกการเขียนในบางเส้นทาง และตรวจยอดก่อนเบิกออกฝั่งเซิร์ฟเวอร์
- มีนำเข้า CSV พร้อมตรวจทาน ใบเบิก/รับ/คืน เลขเอกสาร รายงาน และการรับทราบเอกสาร
- มีข้อมูลล็อตห้องเย็น สูตรผลิต การตรวจสุขภาพ BOM และจุดสั่งซื้อแนะนำจากประวัติจริง
- มีการแจ้งเตือน Telegram และกลไกอัปเดต PWA ที่พยายามหลีกเลี่ยงการรีโหลดระหว่างกรอกข้อมูล

## ก. จุดที่ควรปรับปรุง

### 1. ตรวจสิทธิ์ที่เซิร์ฟเวอร์ให้ครอบคลุมรายการเปลี่ยนข้อมูล — P1

- **พบ:** `doPost` ส่งหลายคำสั่งไปทำงานได้โดยไม่มีด่านตรวจตัวตนร่วม เช่น `rmUpdate`, `rmVerify`, `bomSave`, `bomDelete` และ `crClearLotStock` ไม่ตรวจ session ของผู้เรียกในตัวฟังก์ชัน ส่วน `archiveOldStock` ปฏิเสธเฉพาะกรณีส่ง token มาแล้วไม่ผ่าน แต่กรณีไม่ส่ง token จะผ่านเงื่อนไขนี้
- **ผลกระทบ:** หากโค้ดนี้ถูกใช้จริง ผู้ที่เรียกปลายทางได้อาจเปลี่ยนข้อมูลหรือระบุชื่อผู้ทำรายการเอง โดยไม่ผ่านการเข้าสู่ระบบในหน้าจอ
- **ข้อเสนอ:** กำหนดตารางสิทธิ์รายคำสั่ง ตรวจ session และบัญชีที่ยังใช้งานได้ฝั่งเซิร์ฟเวอร์ และใช้ชื่อจาก session เป็นผู้ทำรายการ แยกทางเรียกงานตามเวลาภายในออกจากทาง HTTP ให้ชัดเจน ประเด็นนี้เป็นการตรวจสิทธิ์ผู้ใช้ ไม่ใช่การเปิด API key ที่เคยสั่งพักไว้
- **เกณฑ์ตรวจรับ:** คำสั่งเปลี่ยนข้อมูลจากผู้ไม่เข้าสู่ระบบหรือบทบาทที่ไม่มีสิทธิ์ต้องถูกปฏิเสธ แม้เรียกตรงโดยไม่ผ่านหน้าจอ
- **อ้างอิง:** `gas_code.js`: `doPost`, `_handleRawMaterialInner`, `handleColdroom`, `archiveOldStock`; `appsscript.json`: `webapp.access`

### 2. ห้ามแจ้งว่าเก็บงานออฟไลน์แล้ว หากบันทึกในเครื่องไม่สำเร็จ — P1

- **พบ:** `_offSave` กลืนข้อผิดพลาดจาก `localStorage.setItem` แต่ `offlineSend` ยังคืน `queued: true` จากนั้นหน้าจอแจ้งว่าเก็บรายการไว้แล้ว
- **ผลกระทบ:** เมื่อพื้นที่เต็มหรือเบราว์เซอร์ไม่อนุญาตให้เก็บข้อมูล ผู้ใช้อาจปิดหน้าต่างโดยเข้าใจว่างานปลอดภัย ทั้งที่รายการไม่ได้อยู่ในคิว
- **ข้อเสนอ:** ให้การบันทึกคิวคืนผลสำเร็จ/ล้มเหลวอย่างชัดเจน เก็บข้อมูลไว้ในแบบฟอร์มเมื่อบันทึกไม่ได้ และพิจารณาที่เก็บคิวแบบ IndexedDB ซึ่งรองรับธุรกรรมได้
- **เกณฑ์ตรวจรับ:** จำลองพื้นที่เต็มแล้วต้องไม่แสดงข้อความว่าเก็บสำเร็จ และผู้ใช้ยังคัดลอกรายละเอียดรายการได้
- **อ้างอิง:** `js/offline.js`: `_offSave`, `offlineSend`; `js/raw.js`: `rawSubmitAction`, `rawSubmitVerify`

### 3. ทำให้การกันรายการซ้ำครอบคลุมงานค้างระยะยาว — P1

- **พบ:** `_opSeen` ใช้ cache 6 ชั่วโมง และเมื่อไม่พบจะตรวจประวัติเพียง 500 แถวท้าย ส่วนห้องเย็นตรวจเฉพาะ cache
- **ผลกระทบ:** รายการที่เซิร์ฟเวอร์ทำสำเร็จแต่คำตอบหาย อาจถูกทำซ้ำหลัง cache หมดและประวัติเดิมพ้น 500 แถว การตั้งยอดห้องเย็นซ้ำก็อาจทับยอดใหม่ที่มีคนแก้ภายหลังได้
- **ข้อเสนอ:** มีทะเบียน `opId` ที่เก็บถาวรตามอายุคิวที่รองรับ ผูกกับคลังและชนิดรายการ พร้อมผลลัพธ์เดิม เช่น เลขเอกสาร แทนการพึ่ง cache เป็นหลัก
- **เกณฑ์ตรวจรับ:** ส่งรายการเดิมซ้ำหลังพ้น 6 ชั่วโมงและมีประวัติใหม่เกิน 500 แถวแล้ว ยอดและเอกสารต้องไม่เปลี่ยนอีก
- **อ้างอิง:** `gas_code.js`: `_opSeen`, `_opRemember`, `rmUpdate`, `crSaveOrUpdateCount`

### 4. รองรับการเขียนสำเร็จเพียงบางส่วน — P1

- **พบ:** `rmUpdate` เปลี่ยนยอดก่อนสร้างเลขเอกสารและเพิ่มประวัติ ส่วน `rmVerify` เปลี่ยนยอดก่อนเพิ่มประวัติ การล็อกกันคนเขียนพร้อมกันไม่ได้ย้อนคืนสิ่งที่เขียนแล้วเมื่อขั้นตอนถัดไปล้มเหลว
- **ผลกระทบ:** ถ้าบันทึกประวัติไม่สำเร็จ ยอดอาจเปลี่ยนไปแล้วแต่ไม่มีหลักฐาน `opId` ทำให้ส่งซ้ำแล้วหักยอดเพิ่มได้
- **ข้อเสนอ:** ออกแบบสถานะรายการก่อนเริ่มเขียน เช่น รอดำเนินการ/เสร็จแล้ว/ต้องตรวจสอบ เก็บยอดก่อนและหลัง และมีทางกู้คืนรายการที่ค้างกลางขั้นตอน แยกความผิดพลาดในการแจ้งเตือนออกจากผลบันทึกสต๊อก
- **เกณฑ์ตรวจรับ:** จำลองความล้มเหลวหลังเปลี่ยนยอดแต่ก่อนเพิ่มประวัติ แล้วส่งซ้ำต้องไม่หักเพิ่ม และต้องค้นหารายการผิดปกติได้
- **อ้างอิง:** `gas_code.js`: `_withLock`, `rmUpdate`, `rmVerify`

### 5. ป้องกันยอดตรวจนับเก่าทับความเคลื่อนไหวใหม่ — P1

- **พบ:** งาน `VERIFY` เก็บยอดสัมบูรณ์ในคิว และ `rmVerify` เขียนยอดนั้นทันทีเมื่อได้รับ โดยไม่ได้ตรวจว่ายอดเปลี่ยนหลังเวลาที่นับหรือไม่
- **ตัวอย่าง:** นับได้ 100 ขณะออฟไลน์ จากนั้นอีกเครื่องเบิก 10 เหลือ 90 เมื่อเครื่องแรกส่งงานได้ ระบบอาจตั้งยอดกลับเป็น 100
- **ข้อเสนอ:** แนบรุ่นข้อมูลหรือเวลาที่เห็นยอดล่าสุด แล้วตรวจความขัดแย้งก่อนตั้งยอด เสนอให้ผู้ใช้ตรวจทานเฉพาะรายการที่ขัดแย้ง โดยไม่บล็อกงานเบิกทั่วไป
- **เกณฑ์ตรวจรับ:** ทดสอบสองเครื่องตามตัวอย่างแล้วไม่สามารถตั้งยอดเก่าทับรายการใหม่โดยไม่มีการแจ้งให้ตรวจสอบ
- **อ้างอิง:** `js/raw.js`: `rawSubmitVerify`; `mobile.html`: การส่ง `VERIFY`; `gas_code.js`: `rmVerify`

### 6. รักษาลำดับคิวและประสานหลายแท็บ — P1

- **พบ:** `offlineSync` ส่งงานตามลำดับ แต่ `offlineSend` ยิงรายการใหม่ตรงเสมอ แม้มีรายการเก่าค้างอยู่ และ `_offSyncing` ป้องกันการส่งซ้ำเฉพาะแท็บเดียว การอ่านแล้วเขียนคิวใน localStorage ไม่มีธุรกรรมข้ามแท็บ
- **ผลกระทบ:** งานใหม่อาจแซงงานเก่า โดยเฉพาะการนับ/เบิก/คืน และสองแท็บอาจเขียนคิวทับกัน แม้เซิร์ฟเวอร์จะช่วยกันบางรายการซ้ำได้
- **ข้อเสนอ:** ให้รายการใหม่ต่อท้ายคิวเมื่อมีงานค้าง ใช้ตัวส่งคิวหลักหนึ่งตัวต่อเบราว์เซอร์ และจัดเก็บคิวด้วยกลไกที่รองรับการเขียนพร้อมกัน
- **เกณฑ์ตรวจรับ:** เปิดสองแท็บ เพิ่มรายการขณะกำลังส่ง แล้วตรวจว่ารายการครบและเรียงลำดับตามกติกาที่กำหนด
- **อ้างอิง:** `js/offline.js`: `offlineSend`, `offlineSync`, `_offSave`, `_offSyncing`

### 7. จัดการคำขอค้างและแยกข้อผิดพลาดชั่วคราวออกจากงานที่ถูกปฏิเสธ — P2

- **พบ:** `_offPost` ไม่มีเวลาสิ้นสุดการรอที่กำหนดโดยแอป ส่วน `offlineSync` ย้ายทุกผลลัพธ์ที่ไม่สำเร็จไปเป็นงานล้มเหลว รวมถึงข้อความระบบกำลังประมวลผลคำขออื่นจาก `_withLock` อีกทั้ง `OFFLINE_MAX_TRIES` ประกาศไว้แต่ยังไม่ถูกนำมาใช้
- **ผลกระทบ:** การเชื่อมต่อค้างทำให้คิวหยุดรอ และเหตุขัดข้องชั่วคราวอาจบังคับให้พนักงานคีย์ใหม่โดยไม่จำเป็น
- **ข้อเสนอ:** กำหนดเวลาเลิกรอ แยกรหัสผิดพลาดที่ลองใหม่ได้กับที่ต้องแก้ข้อมูล และส่งซ้ำด้วย `opId` เดิม เพราะการเลิกรอฝั่งหน้าจอไม่ได้แปลว่าเซิร์ฟเวอร์หยุดทำงาน
- **อ้างอิง:** `js/offline.js`: `_offPost`, `offlineSync`, `OFFLINE_MAX_TRIES`; `gas_code.js`: `_withLock`

### 8. ป้องกันข้อมูลผิดคลังเมื่อสลับหน้าระหว่างโหลด — P1

- **พบ:** `rawLoadData` ใช้ `rawCurrentModule` ตอนเริ่มขอข้อมูล แต่หลัง `await` กลับอ่านตัวแปรเดียวกันเพื่อเลือก cache และแสดงผล โดยไม่ได้ตรวจว่าผู้ใช้เปลี่ยนคลังไปแล้วหรือยัง
- **ผลกระทบ:** หากคำตอบของ SQF มาช้าหลังผู้ใช้สลับไป MLM ข้อมูล SQF อาจแสดงในหน้า MLM และถูกเก็บลง cache ของ MLM
- **ข้อเสนอ:** จับคลังและรหัสคำขอไว้ตั้งแต่เริ่ม ใช้ค่านั้นเป็นชื่อ cache และแสดงผลเฉพาะเมื่อยังเป็นคำขอที่ตรงกับหน้าปัจจุบัน
- **เกณฑ์ตรวจรับ:** จำลองเน็ตช้าแล้วสลับ SQF/MLM หลายครั้ง ข้อมูลและหัวหน้าต้องตรงคลังเสมอ
- **อ้างอิง:** `js/raw.js`: `rawLoadData`, `_rawApplyData`; `js/app.js`: `switchModule`

### 9. แยกข้อมูลออกจาก HTML และคำสั่งในปุ่ม — P1

- **พบ:** ตารางวัตถุดิบประกอบ `onclick` ด้วย `escapeJs(item.Name)` ภายใน attribute ที่ครอบด้วยเครื่องหมายคำพูดคู่ แต่ `escapeJs` ไม่ได้เข้ารหัสสำหรับบริบท HTML attribute เครื่องหมาย backslash ไม่ได้ทำหน้าที่ escape เครื่องหมายคำพูดของ HTML
- **ผลกระทบ:** ชื่อที่มีเครื่องหมายคำพูดอาจทำให้ปุ่มเสีย และข้อมูลที่ถูกสร้างอย่างจงใจอาจแทรก attribute หรือ HTML ได้ จึงควรตรวจทุกจุดที่ใช้รูปแบบเดียวกัน
- **ข้อเสนอ:** สร้างปุ่มแล้วผูกเหตุการณ์ด้วย `addEventListener` และใส่ข้อความด้วย `textContent` แทนการซ้อนข้อความผู้ใช้ในคำสั่ง inline
- **เกณฑ์ตรวจรับ:** ชื่อที่มีเครื่องหมายคำพูดเดี่ยว/คู่ เครื่องหมาย `< > &` ต้องแสดงและกดได้ถูกต้อง โดยไม่ถูกตีความเป็นโค้ด
- **อ้างอิง:** `js/raw.js`: `renderRawInventory` บริเวณปุ่มรับ/เบิก; `js/utils.js`: `escapeJs`, `escapeHtml`

### 10. ตรวจข้อมูลฝั่งเซิร์ฟเวอร์ให้ครบและไม่เปลี่ยนค่าผิดเงียบ ๆ — P2

- **พบ:** `_validateQty` เปลี่ยนค่าผิดหรือค่าติดลบเป็น 0 และตัดค่าสูงเกินเพดานให้เหลือ 9,999,999; `rmVerify` สามารถใช้ค่านั้นตั้งยอดได้ `ddmmyyToIso` ยอมรับวันที่ 31 กุมภาพันธ์และคืนข้อความที่มี `-` โดยไม่ตรวจรูปแบบเต็ม ส่วนเหตุผลเบิก `purpose` บังคับในหน้าจอแต่ `rmUpdate` ไม่ปฏิเสธค่าว่าง
- **ผลกระทบ:** ข้อมูลผิดอาจกลายเป็นยอดศูนย์ วันที่ไม่มีจริง หรือเอกสารขาดเหตุผล
- **ข้อเสนอ:** ส่งข้อผิดพลาดที่ชัดเจนเมื่อข้อมูลไม่ผ่าน ตรวจวันตามปฏิทินจริง และใช้กติกาจำนวน/ทศนิยม/เหตุผลตรงกันทุกช่องทาง
- **อ้างอิง:** `gas_code.js`: `_validateQty`, `ddmmyyToIso`, `rmVerify`, `rmUpdate`; `js/raw.js`: `rawSubmitAction`

### 11. ครอบการเขียนข้อมูลที่เกี่ยวข้องด้วยการล็อกอย่างสม่ำเสมอ — P2

### 12. ทำให้การใช้งานออฟไลน์ไม่พึ่งไฟล์ภายนอกที่ยังไม่ถูกเก็บ — P2

- **ผลกระทบ:** ความพร้อมออฟไลน์ของรูปแบบหน้าและการสแกนอาจต่างกันระหว่างเครื่อง และการโหลดใหม่จาก CDN อาจได้รุ่นต่างจากที่เคยตรวจ
- **ข้อเสนอ:** จัดเก็บไฟล์จำเป็นของแอปไว้กับชุดเผยแพร่ ใช้ CSS ที่เตรียมไว้ และตรึงรุ่นไลบรารี ตรวจทั้งหน้าคอมและมือถือหลังติดตั้งแล้วตัดอินเทอร์เน็ต
- **อ้างอิง:** `index.html`: script ส่วนหัว; `mobile.html`: script ส่วนหัวและตัวสแกน; `sw.js`: `STATIC_ASSETS`, `CDN_URLS`, fetch handler

### 13. กำหนดชุดไฟล์สำหรับเผยแพร่ให้ชัดเจน — P2

- **พบ:** workflow อัปโหลดจาก `path: '.'` ทั้ง repository และผล `git ls-files gas_code.js` ยังพบไฟล์ backend แม้ `.gitignore` ระบุชื่อไฟล์นี้อยู่ การใส่ ignore ไม่ทำให้ไฟล์ที่ติดตามอยู่แล้วหยุดติดตาม
- **ผลกระทบ:** มีโอกาสนำไฟล์เครื่องมือย้ายข้อมูล เอกสารภายใน หรือ backend ที่หน้าเว็บไม่จำเป็นต้องใช้เข้าไปในชุดเผยแพร่ การเปิดเผยโค้ดไม่ได้พิสูจน์ว่ามีข้อมูลลับรั่ว แต่ควรแยกขอบเขตให้ชัด
- **ข้อเสนอ:** เตรียมโฟลเดอร์เผยแพร่ที่มีเฉพาะไฟล์เว็บที่อนุญาต ตรวจรายการไฟล์ก่อน deploy และกำหนดที่เก็บประวัติ backend ให้เหมาะสม โดยไม่ลบไฟล์ออกจากการติดตามทันทีโดยไม่มีแผน
- **อ้างอิง:** `.github/workflows/deploy.yml`: Upload artifact; `.gitignore`; `migrate.html`

### 14. เพิ่มการตรวจอัตโนมัติสำหรับงานสำคัญก่อนเผยแพร่ — P2

- **พบ:** `package.json` ไม่มีคำสั่ง test/lint และ workflow เผยแพร่ไม่มีขั้นตอนตรวจพฤติกรรมหรือไฟล์ที่ PWA ต้องใช้

- **เกณฑ์ตรวจรับ:** ข้อผิดพลาดที่ทำให้ยอดผิดหรือไฟล์สำคัญหายต้องทำให้ขั้นตอนตรวจไม่ผ่านก่อนเผยแพร่ และมีการทดสอบอัปเดตโดยไม่ล้าง cache อย่างน้อยหนึ่งรอบ
- **อ้างอิง:** `package.json`, `.github/workflows/deploy.yml`, `sw.js`

### 15. ลดโค้ดซ้ำและปรับเอกสารให้ตรงกับระบบปัจจุบัน — P2

## ข. สิ่งที่ควรเพิ่มเติมจากความสามารถเดิม

### 17. หน้าติดตามงานค้างและงานส่งไม่ผ่านที่กู้กลับได้ — P2

- ต่อจากคิวเดิม ให้เห็นคลัง ผู้ทำ เวลา รายละเอียด และสถานะของแต่ละงาน
- เก็บ payload และ `opId` ของงานล้มเหลวเพื่อแก้ข้อมูลหรือส่งซ้ำอย่างมีหลักฐาน ปัจจุบัน `_offRecordFailure` เก็บเพียงเวลา ป้ายข้อความ และเหตุผล สูงสุด 20 รายการ จึงกู้รายละเอียดเดิมได้ไม่ครบ
- เพิ่มส่งออกรายการค้างและเลือกจัดการทีละรายการ พร้อมระบุว่าอะไรยังไม่เข้ายอดจริง
- ตกลงพฤติกรรมเมื่อเปลี่ยนผู้ใช้บนเครื่องร่วมกัน เพราะคิวใช้ storage key เดียวทั้งเบราว์เซอร์
- **ฐานที่ต่อยอด:** `js/offline.js`: `_offRecordFailure`, `offlineDetailText`; `js/auth.js`: `logout`

### 18. แสดงอายุข้อมูลและยอดที่ยังรอส่งอย่างต่อเนื่อง — P2

- แสดงยอดที่ยืนยันแล้วแยกจากผลของงานค้างของเครื่องนี้ เพื่อไม่ให้ผู้ใช้เข้าใจว่ายอดเดิมยังพร้อมเบิกทั้งหมด
- ปัจจุบัน cache มีเวลาเก็บอยู่แล้ว แต่ `cacheGet` คืนเฉพาะข้อมูล และหน้าโหลดวัตถุดิบไม่ได้กำหนดอายุสูงสุด
- **ฐานที่ต่อยอด:** `js/app.js`: `cacheSet`, `cacheGet`; `js/raw.js`: `rawLoadData`, `rawSubmitAction`

### 19. เชื่อมใบเบิกกับใบสั่งผลิตเพื่อเทียบใช้จริงกับสูตร — P3

- เพิ่มตัวเลือกใบสั่งผลิตในการเบิก โดยยังให้ทำงานต่อได้หากไม่มีใบสั่งผลิตที่ตรง และใช้การรับทราบภายหลัง
- ใช้รหัสอ้างอิงที่แน่นอนแทนการจับคู่จากข้อความ “ใช้กับงานอะไร” เพียงอย่างเดียว
- เมื่อเชื่อมข้อมูลพร้อมแล้วจึงต่อยอดรายงานรายสัปดาห์ว่าใช้จริงต่างจากสูตรเท่าใด พร้อมเหตุผลและช่องทำเครื่องหมายตรวจแล้ว
- ระหว่างที่ยังไม่ผูกรายการ ต้องระบุว่าการเทียบเป็นภาพรวม ไม่อ้างว่าเป็นความสูญเสียเฉพาะล็อตหรือเฉพาะคน และไม่ทำอันดับพนักงานหรือแจ้งเตือนทุกครั้งที่เกินเกณฑ์
- **ฐานที่ต่อยอด:** `gas_code.js`: `rmUpdate`, `bomCalcWorkOrder`; โมดูลใบสั่งผลิตและ BOM ที่มีอยู่
