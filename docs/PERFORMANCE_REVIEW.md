# แนวทางเพิ่มความเร็ว AppStock

วันที่ตรวจ: 16 กันยายน 2569

## ข้อสรุป

มีโอกาสเพิ่มความเร็วได้โดยยังใช้ Google Apps Script และ Google Sheets เดิม จุดที่ควรเริ่มคือ **ลดงานที่ต้องรอขณะบันทึก ลดการโหลดทั้งคลังซ้ำ และลดการเรียกเซิร์ฟเวอร์ทีละรายการ** จากนั้นปรับการแสดงผลบนมือถือ

รายงานนี้ตรวจจากโค้ดในเครื่องรอบปัจจุบัน ซึ่งมีการปรับปรุงเพิ่มจากรอบรายงานก่อนแล้ว ไม่ได้วัดเวลาระบบจริง ไม่ได้แก้โค้ดแอป ไม่ได้เปลี่ยนข้อมูล และไม่ได้ deploy ผลด้านความเร็วเป็นสิ่งที่คาดจากเส้นทางโค้ด ยังไม่ใช่ตัวเลขที่ยืนยันด้วยการทดสอบ

## สิ่งที่ทำไว้แล้ว ไม่ควรเสนอทำซ้ำ

- GET วัตถุดิบมี cache ฝั่งเซิร์ฟเวอร์ 5 นาที และล้างเมื่อมีคำสั่งเขียนข้อมูล
- เส้นเทรนด์มี cache ทั้งหน้าจอและเซิร์ฟเวอร์ และโหลดตามหลังตารางหลัก
- ประวัติล่าสุดของหน้าวัตถุดิบอ่านเพียง 30 แถวท้าย ไม่ได้อ่านประวัติทั้งหมดในคำขอนี้
- ตารางวัตถุดิบและล็อตห้องเย็นหน้าคอมแสดงเป็นชุด ชุดละ 50 รายการ
- หน้า EXEC โหลดข้อมูลสามคลังพร้อมกันด้วย `Promise.all` อยู่แล้ว
- Tailwind ถูกเตรียมเป็นไฟล์ CSS แล้ว และ Chart.js/ตัวสแกน/QRCode เก็บไว้ในโปรเจกต์
- PWA เก็บไฟล์แอปไว้ในเครื่องแล้ว จึงต้องแยกการเปิดครั้งแรกกับการกลับมาเปิดซ้ำตอนวัดผล

## ข้อเสนอเรียงตามจุดที่น่าจะคุ้มค่า

### 1. แยกการส่ง Telegram ออกจากเวลารอบันทึก — คาดว่าคุ้มค่าสูง

**พบในโค้ด:** `rmUpdate` และ `rmVerify` เรียก `sendAlert` ก่อนคืนผลให้ผู้ใช้ เส้นทางนี้อยู่ภายใน `_withLock` ส่วน `_crSendTelegramRaw` ส่ง HTTP ไปแต่ละ chat ID ตามลำดับ

**ผล:** ผู้ใช้รอทั้งการบันทึกสต๊อกและการส่งข้อความ ขณะเดียวกันรายการอื่นอาจต้องรอล็อกต่อ แม้การบันทึกหลักทำเสร็จแล้ว หาก Telegram ช้าจะกระทบเวลาบันทึกด้วย

**แนวทาง:** บันทึกสต๊อก ประวัติ และงานแจ้งเตือนลงคิวถาวรให้ครบก่อนคืนผล จากนั้นมีผู้ประมวลผลคิวส่ง Telegram แยกต่างหาก มีสถานะส่งแล้ว/รอลองใหม่ และอ้างอิงรหัสรายการเดิม

**ข้อแลกเปลี่ยน:** ข้อความ Telegram จะตามมาภายหลัง ต้องกำหนดเวลาหน่วงที่ยอมรับได้ หากใช้ time-driven trigger ของ GAS สามารถกำหนดรอบได้ถี่ถึงรายนาที แต่ไม่ควรรับประกันเวลาส่งตรงวินาที และต้องดูโควตาด้วย ([เอกสาร Google](https://developers.google.com/apps-script/guides/triggers/installable))

**ทางเลือกเปลี่ยนน้อยกว่า:** ย้ายการส่งออกจากช่วงถือล็อก จะช่วยคนที่บันทึกพร้อมกัน แต่ผู้กดบันทึกยังต้องรอ Telegram หาก HTTP response ยังไม่ถูกคืน ต้องไม่เรียกทางเลือกนี้ว่าลดเวลารอของผู้ใช้ได้ทั้งหมด

**อ้างอิง:** `gas_code.js`: `_handleRawMaterialInner`, `rmUpdate`, `rmVerify`, `sendAlert`, `_crSendTelegramRaw`

### 2. หลังบันทึกสำเร็จ อัปเดตเฉพาะสินค้าที่เปลี่ยน — คาดว่าคุ้มค่าสูง

**พบในโค้ด:** หน้าคอมเรียก `rawLoadData()` หลังบันทึก และมือถือเรียก `loadData()` ทั้งชุด ฝั่งห้องเย็นบางทางเรียกทั้งค้นหาล็อตและ overview ใหม่

**แนวทาง:** ให้คำตอบการบันทึกคืนข้อมูลสินค้าหรือล็อตล่าสุด ยอดใหม่ เลขเอกสาร และรุ่นข้อมูล แล้วปรับแถวและตัวเลขสรุปเฉพาะส่วนที่เปลี่ยน ดึงข้อมูลคลังใหม่เบื้องหลังเมื่อจำเป็น

วัตถุดิบมี `slip.balance` ในผลลัพธ์อยู่แล้ว จึงมีฐานสำหรับต่อยอด แต่ต้องรองรับผลลัพธ์การส่งซ้ำและการตรวจนับที่ยังไม่ได้คืนข้อมูลครบเท่ากัน

**ประโยชน์:** ตัดการรออ่านทั้งคลังซ้ำหลังงานหนึ่งรายการ ลดหน้าจอกะพริบและจำนวนคำขอ

**เงื่อนไข:** อัปเดตเป็นยอดยืนยันเมื่อเซิร์ฟเวอร์ตอบสำเร็จเท่านั้น งานออฟไลน์ต้องแสดงว่ารอส่ง และคำตอบอ่านเก่าที่มาช้าต้องไม่ทับยอดเพิ่งบันทึก

**อ้างอิง:** `js/raw.js`: `rawSubmitAction`, `rawSubmitVerify`; `mobile.html`: `confirmAction`, `confirmCrCount`; `js/coldroom.js`: `crSaveCount`

### 3. รวมการขอข้อมูลรายงานหลายสินค้าเป็นครั้งเดียว — คาดว่าคุ้มค่าสูงเมื่อรายงานมีหลายรายการ

**พบในโค้ด:** `crPrintActualReport` วน `await crCallServer("getProductAndBalances")` ทีละสินค้า ฝั่งเซิร์ฟเวอร์แต่ละรอบอ่านชีตสินค้าและสต๊อกใหม่

**แนวทาง:** เพิ่มคำขอรับหลายบาร์โค้ดพร้อมกัน อ่านชีตสองชุดครั้งเดียว สร้างแผนที่ข้อมูล แล้วคืนเฉพาะล็อตที่รายงานต้องใช้

**ตัวอย่างเชิงโครงสร้าง:** รายงาน 20 สินค้า จากเดิมประมาณ 20 คำขอแยก เหลือหนึ่งคำขอแบบรวม ไม่ได้หมายความว่าจะเร็วขึ้น 20 เท่า เพราะยังมีเวลาคำนวณและส่งข้อมูล

**ข้อควรเลือก:** การยิง 20 คำขอพร้อมกันอาจยังอ่านชีตซ้ำ 20 รอบ จึงควรแก้ให้รวมงานฝั่งเซิร์ฟเวอร์ก่อน ส่วนงานเปลี่ยนยอดหลายรายการต้องออกแบบผลสำเร็จบางส่วนและรหัสกันซ้ำ ไม่เร่งด้วยการยิงขนานอย่างเดียว

**อ้างอิง:** `js/coldroom.js`: `crPrintActualReport`, `crBulkRemove`; `gas_code.js`: `crGetProductAndBalances`

### 4. แสดงข้อมูลที่มีในเครื่องก่อน แล้วตรวจข้อมูลใหม่ — ช่วยให้เห็นหน้าจอเร็ว

**พบในโค้ด:** `rawLoadData` รอเครือข่ายก่อน ใช้ cache เมื่อโหลดล้มเหลวเท่านั้น ห้องเย็นใช้ cache เป็นทางสำรองเช่นกัน

**แนวทาง:** ถ้ามีข้อมูลเดิม ให้แสดงทันทีพร้อมป้ายเวลาและ “กำลังตรวจข้อมูลล่าสุด” แล้วแทนที่เมื่อข้อมูลใหม่มาถึง คงหน้ารายการเดิมไว้ระหว่าง refresh แทนการบังทั้งหน้าจอ

**ประโยชน์:** เปิดกลับมาดูหรือสลับคลังได้คล่องขึ้น แต่ไม่ได้ทำให้เซิร์ฟเวอร์อ่านข้อมูลเร็วขึ้น และไม่ช่วยเครื่องที่ยังไม่มี cache

**เงื่อนไข:** ไม่แสดงข้อมูลเก่าว่าเป็นยอดปัจจุบัน การตรวจยอดก่อนบันทึกต้องอยู่ที่เซิร์ฟเวอร์เช่นเดิม เก็บ cache แยกคลังและป้องกันคำตอบเก่าทับคำตอบใหม่

**อ้างอิง:** `js/raw.js`: `rawLoadData`, `rawSetDataAge`; `js/coldroom.js`: `crLoadOverview`; `js/app.js`: `cacheSet`, `cacheGet`

### 5. เพิ่ม cache ห้องเย็นและแยกข้อมูลตามหน้าที่ใช้งาน — คาดว่าคุ้มค่าปานกลางถึงสูง

**พบในโค้ด:** `crGetStartupOverview` อ่านสินค้าและสต๊อกทั้งชีตทุกครั้ง และส่งทั้ง `allLots`, `totalByProduct`, `expiringLots`, `expiredLots` มือถือใช้ `allLots` เป็นหลักแต่รับส่วนอื่นมาด้วย

**แนวทาง:**

1. แยกข้อมูลสินค้าที่เปลี่ยนไม่บ่อยออกจากยอดล็อตที่เปลี่ยนบ่อย
2. ทำ cache overview อายุสั้น และล้างหรือเปลี่ยนรุ่นเมื่อทุกเส้นทางเขียนสต๊อก/สินค้า/เกณฑ์เตือนสำเร็จ
3. เพิ่มรูปแบบคำตอบสำหรับมือถือและหน้าสรุป ส่งเฉพาะข้อมูลที่หน้านั้นใช้จริง
4. รวมข้อมูลสำหรับเปิดห้องเย็นกับ dropdown เมื่อใช้ข้อมูลต้นทางเดียวกัน

**เงื่อนไข:** ค่าจำนวนวันก่อนหมดอายุเปลี่ยนเมื่อข้ามวันแม้ไม่มีคนบันทึก จึงต้องคำนึงถึงวันไทยใน cache key/อายุ cache ด้วย และต้องมีปุ่มดึงใหม่สำหรับกรณีแก้ชีตตรง

**อ้างอิง:** `gas_code.js`: `crGetStartupOverview`; `js/coldroom.js`: `initColdroom`, `crLoadProductDropdown`; `mobile.html`: `loadData`

### 6. ตรวจว่า cache วัตถุดิบใช้งานได้จริงเมื่อข้อมูลโต — ควรตรวจต้น ๆ

**พบในโค้ด:** `doGet` cache JSON ทั้งก้อนเมื่อ `json.length < 95000` และกลืนข้อผิดพลาดของ `cache.put` การนับความยาวข้อความไม่เท่ากับขนาดไบต์ โดยเฉพาะข้อความภาษาไทย

**ผลที่เป็นไปได้:** ชุดข้อมูลอาจเกินขนาดที่ cache รับได้แต่ไม่มีสัญญาณให้เห็น จึงกลับไปอ่านชีตทุกครั้ง ทั้งที่คิดว่ามี cache แล้ว ขณะนี้ยังไม่ได้วัด payload จริงจึงไม่ยืนยันว่าเกิดขึ้นแล้ว

**แนวทาง:** วัดขนาด UTF-8 และอัตรา cache hit/miss แยกประวัติ สินค้าเลิกใช้ และข้อมูลสำหรับสร้างรายการใหม่ออกจากคำตอบหลักเมื่อไม่จำเป็น หากแบ่ง cache เป็นหลายส่วน ต้องมีหมายเลขรุ่นเดียวกันและอ่านใหม่เมื่อส่วนใดหาย

Google ระบุว่าค่าแต่ละ key เก็บได้ไม่เกิน 100KB และอาจถูกนำออกก่อนเวลาหมดอายุที่ขอไว้ จึงต้องมีทางอ่านต้นฉบับเสมอ ([เอกสาร Cache](https://developers.google.com/apps-script/reference/cache/cache))

**อ้างอิง:** `gas_code.js`: `doGet`, `getRawMaterials`, `_rawCacheBust`

### 7. สรุปประวัติรายวันแทนการอ่านประวัติทั้งหมดซ้ำ — คุ้มค่ามากขึ้นเมื่อประวัติโต

**พบในโค้ด:** `rmTrends` และ `rmRopStats` อ่าน History ทั้งชีตด้วย `getDataRange()` แล้วค่อยกรองช่วงเวลา โดยเทรนด์มี cache อยู่แล้ว แต่ cache miss ยังต้องคำนวณจากต้นทาง

**แนวทาง:** มีข้อมูลสรุปต่อวัน/คลัง/SKU สำหรับยอดเบิก คืน จำนวนรายการ และข้อมูลที่จำเป็นต่อ ROP คำนวณช่วง 30/90 วันจากสรุปนี้แทนแถวประวัติทั้งหมด

**เงื่อนไขสำคัญ:** ต้องรองรับรายการออฟไลน์ที่ส่งย้อนหลังและการแก้ประวัติในชีตโดยตรง มีการคำนวณใหม่หรือกระทบยอดตามรอบ และรักษาวิธีคิดวันเริ่มใช้/วันไม่มีรายการ/ยอดคืนของสูตรเดิม

ไม่ควรอ่านแค่แถวท้ายตามวันที่แล้วหยุดทันที เพราะเวลาที่เกิดงานจริงอาจไม่เรียงตามเวลาที่ส่งเข้าระบบ

**อ้างอิง:** `gas_code.js`: `rmTrends`, `rmRopStats`, `_eventTime`; `js/raw.js`: `rawLoadTrends`

### 8. ลดจำนวนครั้งที่อ่านและเขียน Google Sheets — ทำเฉพาะทางที่วัดแล้วแพง

**พบในโค้ด:** การแก้ล็อตและข้อมูลบางส่วนใช้ `setValue` หลายครั้ง และมีหลายฟังก์ชันอ่านหัวตาราง/ข้อมูลเดิมซ้ำภายในคำขอเดียว

**แนวทาง:** อ่านช่วงที่ต้องใช้เป็นชุด เก็บแผนที่หัวคอลัมน์และข้อมูลที่อ่านแล้วภายในคำขอ คำนวณในหน่วยความจำ และเขียนช่วงที่แก้เป็นชุดเมื่อเหมาะสม ย้ายการตรวจโครงสร้างชีตที่ไม่จำเป็นทุกครั้งไปเป็นขั้นตอนจัดการรุ่นโครงสร้าง โดยยังมีทางรองรับชีตเก่า

ต้องไม่เขียนทั้งแถวทับสูตรหรือข้อมูลที่อีกคนเพิ่งเปลี่ยน และต้องรักษาการล็อกส่วนที่เปลี่ยนยอด

แนวทางลดการเรียกบริการและอ่าน/เขียนแบบชุดตรงกับคำแนะนำของ Google สำหรับ Apps Script ([Best Practices](https://developers.google.com/apps-script/guides/support/best-practices))

**อ้างอิง:** `gas_code.js`: `crSaveOrUpdateCount`, `crClearLotStock`, `ensureColumns`, `getRawMaterials`

### 9. รวมคำขอซ้ำที่กำลังรอ และโหลดหน้าสรุปทีละส่วน — ลดการรอที่ไม่จำเป็น

**พบในโค้ด:** มีตัวกระตุ้น refresh จากการสลับหน้า กลับแท็บ และหลังบันทึก ห้องเย็นมีช่วงกันถี่ 8 วินาทีแล้ว แต่ยังควรมีตัวรวมคำขอที่กำลังรอ ส่วน EXEC รอ `Promise.all` ให้ครบสามคลังก่อนวาดทั้งหมด

**แนวทาง:** คำขออ่านชนิดเดียวกันและคลังเดียวกันที่เกิดพร้อมกันให้รอผลร่วมกัน ใช้รุ่นข้อมูลแยกคำขอก่อน/หลังเขียน สำหรับ EXEC ให้ส่วนแต่ละคลังแสดงเมื่อพร้อม และระบุเวลาของแต่ละส่วน

**เงื่อนไข:** KPI ที่ต้องรวมหลายคลังต้องแสดงว่ายังไม่ครบจนข้อมูลมาครบ ไม่รวมค่าบางส่วนแล้วแสดงเป็นยอดทั้งหมด และอย่าให้คำขอเก่าก่อนบันทึกตอบทับรุ่นใหม่

**อ้างอิง:** `js/app.js`: `_refreshActiveModule`; `js/coldroom.js`: `crRefreshIfStale`; `js/exec.js`: `loadExecDashboard`

### 10. แสดงรายการมือถือทีละชุดและลดการวาดซ้ำระหว่างพิมพ์ — เหมาะกับเครื่องหน้างาน

**พบในโค้ด:** `mobile.html` ใช้ `filt.map(...).join("")` แสดงทุกรายการ และ `filterList` เรียกวาดใหม่เมื่อค้นหา ต่างจากหน้าคอมที่แบ่งรายการแล้ว

**แนวทาง:** เริ่มแสดง 30–50 รายการ เพิ่มปุ่มแสดงต่อหรือแสดงเฉพาะส่วนที่อยู่บนจอ และหน่วงการค้นหาประมาณ 150–250 มิลลิวินาทีเพื่อไม่วาดทุกตัวอักษรถี่เกินไป ใช้การค้นหาบนข้อมูลทั้งหมดก่อนแบ่งหน้าผลลัพธ์

**ประโยชน์:** ช่วยการเลื่อนและพิมพ์บนมือถือเมื่อมีหลายร้อยรายการ แต่ไม่ลดเวลารอเซิร์ฟเวอร์

**อ้างอิง:** `mobile.html`: `renderList`, `filterList`, `populateDropdown`

### 11. โหลดกราฟและตัวสแกนเมื่อจะใช้งาน — ช่วยการเปิดแอปและใช้หน่วยความจำ

**พบในโค้ด:** หน้าคอมโหลด Chart.js และ html5-qrcode ใน `<head>` แบบ script ปกติ แม้ยังไม่เปิดกราฟหรือสแกน ขนาดไฟล์ในเครื่องประมาณ 206KB และ 375KB ตามลำดับ ก่อนการบีบอัดระหว่างส่ง

**แนวทาง:** โหลดเมื่อเปิดฟีเจอร์ หรือใช้ `defer` โดยรักษาลำดับ dependency และแยกส่วนที่เรียกไลบรารีไว้ให้ถูกต้อง ยังคง precache ไฟล์จำเป็นสำหรับออฟไลน์ได้

**ข้อจำกัด:** ถ้ายัง precache ไฟล์เหล่านี้ การติดตั้ง PWA ครั้งแรกยังดาวน์โหลดไฟล์อยู่ ประโยชน์ของการโหลดเมื่อใช้คือเลื่อนการประมวลผล JavaScript ออกจากตอนเปิดหน้า ไม่ควรอ้างว่าตัดปริมาณดาวน์โหลดทั้งหมด

**อ้างอิง:** `index.html`: script ใน head; `js/vendor/chart.umd.min.js`, `js/vendor/html5-qrcode.min.js`; `sw.js`

## วิธีวัดก่อนตัดสินใจแก้

ใช้ข้อมูลทดสอบที่มีขนาดใกล้ของจริงและมือถือที่ใช้หน้างาน แยกทดสอบเปิดครั้งแรก/เปิดซ้ำ, cache hit/miss และ Wi-Fi/อินเทอร์เน็ตมือถือ หลีกเลี่ยงการสร้างรายการทดสอบปะปนกับสต๊อกจริง

| สิ่งที่วัด | จุดเริ่ม–จุดสิ้นสุด | ใช้เลือกข้อเสนอ |
|---|---|---|
| เวลาเห็นรายการครั้งแรก | เปิดคลัง → เห็นรายการที่อ่านได้ | 4, 10, 11 |
| เวลาข้อมูลสดพร้อม | เปิดคลัง → คำตอบใหม่แสดงครบ | 5, 6, 8, 9 |
| เวลาบันทึกจริง | กดยืนยัน → เซิร์ฟเวอร์ยืนยันและยอดใหม่แสดง | 1, 2, 8 |
| เวลารอในเซิร์ฟเวอร์ | รอล็อก / อ่านชีต / เขียนชีต / Telegram แยกกัน | 1, 7, 8 |
| เวลารายงานหลายสินค้า | เปิดรายงาน → พร้อมพิมพ์ | 3 |
| เวลาค้นหา/เลื่อน | พิมพ์ → ผลลัพธ์วาดเสร็จ | 10 |
| ปริมาณงาน | จำนวน API calls / ขนาดคำตอบ UTF-8 / cache hit | 2, 3, 5, 6, 9 |

ควรเก็บหลายรอบ เช่น 20–30 ครั้งต่อสถานการณ์ ดูค่ากลางและค่าช้ากว่าปกติ (p95 แบบคร่าว ๆ) แทนการตัดสินจากรอบเดียว หากต้องใช้ p95 เป็นเกณฑ์จริงควรเก็บจำนวนตัวอย่างเพิ่ม แยกเวลาเก็บข้อมูลจากเซิร์ฟเวอร์ออกจากเวลาวาดหน้าจอ

ตัววัด `_gasLastMs` ในหน้าวัตถุดิบปัจจุบันช่วยดูเวลาขอข้อมูลรวมได้ แต่ยังแยกไม่ได้ว่าเสียเวลาที่ล็อก ชีต เครือข่าย หรือการส่งแจ้งเตือน

## ชุดงานที่แนะนำให้เริ่มเมื่ออนุมัติให้พัฒนา

1. **วัดก่อน:** เวลาอ่าน/เขียน/Telegram/รอล็อก และตรวจ cache hit กับขนาดข้อมูลจริง
2. **งานเปลี่ยนน้อยและตรวจผลตรงไปตรงมา:** รวมคำขอรายงานหลายสินค้า อัปเดตเฉพาะแถวหลังบันทึก และแบ่งรายการมือถือ
3. **งานที่น่าลดเวลารอบันทึกได้มาก:** คิว Telegram ถาวรพร้อมวิธีส่งซ้ำและติดตามผล
4. **งานเร่งหน้าอ่าน:** แสดงข้อมูลเดิมก่อน เพิ่ม cache ห้องเย็น และลดข้อมูลในคำตอบ
5. **เมื่อประวัติเริ่มเป็นตัวถ่วง:** ข้อมูลสรุปรายวันและปรับการอ่าน/เขียนชีตตามหลักฐานการวัด

ยังไม่ควรให้ตัวเลขว่าเร็วขึ้นกี่เปอร์เซ็นต์หรือเหลือกี่วินาทีจนกว่าจะได้ค่าก่อนและหลังบนอุปกรณ์/ข้อมูลเดียวกัน และไม่ควรถอดการตรวจสิทธิ์ การล็อกยอด หรือการกันรายการซ้ำเพื่อแลกความเร็ว
